Change Requests as Rules · Unattended Uploader

Every vehicle carries a list of commercial products that a daily process sets from a rule matrix. Changes requested outside the matrix were applied by hand and quietly undone the next morning, and every bulk change meant uploading files to an internal tool by hand and checking the result. I turned each request into a rule the daily process respects, and built a small service that uploads the resulting files on its own and reports what really happened. In October the uploader moved from a browser session to an internal API, as a set of n8n workflows.

The problem

A daily process sets each vehicle's products from a matrix. Any exception, such as a car that should keep a product it would normally lose, had to be applied by hand, and the next morning the process put things back as the matrix said. People fixed the same cars again and again, and nobody could say why a given car had a given product.

On top of that, every bulk change went through an internal tool that takes a file, one upload at a time, with the result checked by hand afterwards.

How it works

  • Exceptions become rules. A request says what should change, for which vehicles and why. Once a person approves it, it becomes a rule with an author, a reason and an expiry date, and the daily process applies it instead of undoing it.
  • Rules expire. Every exception has an end date, so they do not pile up forever and the matrix stays the default.
  • Files are generated, never typed. The output of the daily process is written straight into the format the upload tool expects.
  • The uploader decides by content, not by name. It recognises which kind of upload a file is by comparing its columns with what each kind expects, so a renamed file still goes to the right place and an unknown one is rejected instead of guessed.
  • Heavy files are split into parts that run in parallel, and the service waits for the tool's real result before reporting, rather than reporting that it clicked a button.
  • The outcome goes to Slack with the links, so the person who asked for the change sees that it happened.

October: from a browser to an API

The first uploader drove the internal tool through a browser session that a person renewed every morning. When the tool closed the door to automated access, I asked the platform team for an API route instead of working around it. Two weeks later the first actions were open to automations, and the uploader became a set of n8n workflows.

  • One workflow per kind of change, each with its own service account and only the permissions it needs.
  • Safe to run twice. A row that is already applied comes back as "no change", so reprocessing a file only applies what was missing.
  • Retries done right. When the API is busy it says how long to wait, and only those rows are repeated.
  • A results file in plain words next to each upload, one line per row, and one Slack message with the counts.
  • A watchdog uploads a file again, once, if it has no result after half an hour, and alerts the owners if that fails too.

Results

  • About 25 hours a month of manual work removed between the repeated fixes and the manual uploads.
  • Every product on every vehicle can now be explained: either the matrix says so, or a rule with a name and a reason does.

What I learned

  • If a process keeps undoing people's work, the fix is usually to give the exception a proper home, not to ask people to be faster.
  • Automating a browser is fragile; checking the real result after every step is what makes it trustworthy.
  • Expiry dates are the cheapest governance there is.
  • When a system closes the door to automation, ask for a proper door instead of picking the lock.
